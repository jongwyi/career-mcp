# 자원 사용 개선 설계

> 상태: **구상만.** 구현 전.
> 측정 시점: 2026-07-26 · 공고 12,474건(진행중 48) · 프로필 59건

---

## 1. 측정 — 어디에 쓰이는가

```
jobs_match(limit=24) 응답

프로필 (evidence 포함)      6,996자   ≈ 2,798토큰   29%
후보 24건                 17,072자   ≈ 6,828토큰   71%
  └ requirements 제외 시    5,458자   ≈ 2,183토큰
──────────────────────────────────────────────
합계                      24,068자   ≈ 9,627토큰

DB 조회 시간              0.68초
후보 1건당                 711자     ≈ 284토큰
요건 총 262개 (6개 상한 표시, 137개는 이미 잘림)
```

`/search_intern` 1회 실행의 총 비용 (추정):

| 구간 | 토큰 |
|---|---|
| `jobs_match` 응답 | ~9,600 |
| Claude 분석 출력 (상위 5 상세 + 19 요약) | ~3,000~5,000 |
| `match_save` 왕복 | ~1,000~2,000 |
| **합계** | **~15,000** |

## 2. 진단 — 통념과 다른 두 가지

**"모든 공고를 순회한다"는 사실이 아니다.**
SQL 이 12,474건을 24건으로 걸러 LLM 에 넘긴다. 걸러내는 비용은 0.68초다.
수집도 증분이라 최근 실행에서 실제로 가져온 건 **1건**이었다.
**수집과 저장은 문제가 아니다.**

**병목은 두 가지다.**

1. **요건을 전부 미리 보낸다.** requirements 가 응답의 절반 가까이(11,614자)인데,
   깊게 보는 건 상위 5건뿐이다. 나머지 19건의 요건은 읽히지도 않고 버려진다.
2. **매번 처음부터 다시 판단한다.** 어제 65점을 준 22건을 오늘 또 읽고 또 평가한다.
   실제로 바뀐 건 1~2건이다.

## 3. 개선안 — 효과 순

### ① 평가 캐시 — 안 바뀐 건 다시 평가하지 않는다

**반복 사용에서 효과가 가장 크다.** 이 시스템은 매일 쓰는 물건이고,
어제와 오늘의 차이는 신규 공고 1~2건뿐이다.

무효화 조건을 정확히 잡는 게 설계의 전부다.

```
jobs.content_hash      = sha256(requirements + preferred + deadline + education)
profile_revision       = fact 추가/수정/보류 시 증가하는 카운터 (단일 정수)

match_results 에 평가 당시의 job_hash 와 profile_revision 을 함께 저장
→ 지금 값과 같으면 재평가 불필요
```

`jobs_match` 응답이 후보를 두 갈래로 나눈다.

```json
{
  "fresh":  [ { 전체 정보 + requirements } ],       // 새로 평가할 것
  "cached": [ { job_id, title, score, 한 줄 요약 } ] // 지난 평가 그대로
}
```

**주의 — 프로필이 바뀌면 전부 무효화하는 건 과하다.**
skill 하나 추가했다고 24건을 재평가할 이유는 없다.
절충: `profile_revision` 이 바뀌면 **상위 N건만** 재평가하고 나머지는 캐시를 유지하되
"프로필이 바뀌어 재평가가 필요할 수 있음"을 표시한다.

| | 1회차 | 2회차 이후 |
|---|---|---|
| 평가 대상 | 24건 | 1~2건 |
| 예상 토큰 | ~9,600 | ~1,500 |

### ② 2단계 조회 — 훑고 나서 파고든다

지금은 24건의 요건을 다 보낸다. 사람의 실제 판단 순서와 다르다 —
제목·기관·마감·직무로 훑고, 관심 가는 것만 요건을 본다.

```
1단계  jobs_match(detail=false)
       title / company / deadline / days_left / location
       / job_field / education / headcount / previous_score
       → 2,183 토큰 (68% 절감)

2단계  job_requirements(job_ids=[상위 5~8])
       그때만 요건을 로드
       → 5건 × 284 = 1,420 토큰
```

합계 6,828 → 약 3,600 토큰. **47% 절감.**

부수 효과가 하나 더 있다. 지금은 요건 262개 중 137개가 이미 6개 상한에서 잘려 있다.
2단계에서는 상위 후보의 **요건 전문**을 볼 수 있어 분석이 오히려 깊어진다.

### ③ 프로필 계층화

kind 별 비중:

| kind | 건수 | 토큰 | 요건 대조에 쓰이나 |
|---|---|---|---|
| experience | 19 | 646 | ✅ 근거 |
| skill | 10 | 408 | ✅ 근거 |
| goal | 11 | 390 | ❌ 방향 |
| preference | 9 | 306 | ❌ 방향 |
| weakness | 6 | 210 | △ gap 후보 |
| strength | 4 | 142 | ✅ 근거 |

**`goal`·`preference` 는 요건 충족의 근거가 될 수 없다.** 방향을 정하는 값이지
"이 요건을 만족한다"의 증거가 아니다. 매번 전문을 보낼 이유가 없다.

**`evidence` 는 지원서 재료를 쓸 때만 필요하다.** 점수를 매길 때는 `content` 로 충분하다.

```
기본 응답     skill/experience/strength 의 content 만    ≈ 700토큰
             goal/preference 는 한 줄 요약으로 압축
필요할 때     profile_evidence(fact_ids=[...])           상위 후보 분석 시에만
```

2,798 → 약 1,000 토큰. **64% 절감.**

### ④ 기본 개수 축소 — 즉시, 무비용

`limit` 기본값 24 → **8**.

사람이 한 번에 검토하고 행동할 수 있는 건 5~8건이다.
24건을 받아도 실제로 지원을 검토하는 건 상위 몇 개뿐이다.
"더 보여줘"로 확장하면 된다.

**코드 변경 한 줄이고 효과는 선형이다.** 먼저 해볼 값어치가 있다.

### ⑤ 수집 범위 제한 (부차적)

수집은 이미 싸지만 백필이 비효율적이다.

- `--full` 이 수년치 12,474건을 가져온다. 진행중은 48건뿐이다
  → `--since-days 365` 기본값. 과거 공고는 필요할 때만
- raw payload 해시를 비교해 **내용이 같으면 raw 재저장을 건너뛴다**
  → prune 이 나중에 지울 행을 애초에 만들지 않는다

## 4. 예상 효과

|---|---|---|---|
| `jobs_match` 응답 | 9,600 | ~3,000 | ~1,500 |
| 분석 출력 | 3,000~5,000 | ~2,500 | ~800 |

## 5. 하지 말아야 할 것

**벡터 검색은 지금 필요 없다.** 후보가 24건인데 임베딩을 도입하는 건 과잉이다.
공고가 수천 건 규모로 늘고 규칙 필터로 못 좁힐 때가 도입 시점이다.

**수집을 줄이는 건 답이 아니다.** 증분 수집은 하루 1건이고 비용이 없다.
공고를 덜 모으면 추천 품질만 떨어진다.

**요건을 더 잘라내는 것도 답이 아니다.** 지금도 137개가 잘려 있다.
잘라내는 게 아니라 **필요할 때만 가져오는 것**이 방향이다.

## 6. 착수 순서 제안

```
④ 기본값 8         한 줄. 즉시 3배 절감
② 2단계 조회       중간 규모. 분석 품질도 개선됨
③ 프로필 계층화     중간 규모
① 평가 캐시        가장 크지만 무효화 규칙 설계가 필요 — MVP 사용 결과를 보고
```

①을 마지막에 두는 이유: 무효화 조건이 실사용 패턴에 달려 있다.
매일 쓰는지 주 1회 쓰는지, 프로필을 얼마나 자주 고치는지에 따라
캐시 유효 기간과 재평가 범위가 달라진다. **쓰면서 관찰한 뒤 정하는 게 맞다.**
